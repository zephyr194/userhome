# SKILLHUB：工具集中的 Skill 目录（只读）

> 来源：https://oss-dd-public.nioint.com/queqiao/fms/archie.zheng/v2.4/skill-cheatsheet.html （SKILL 速查 v2.4，嵌入数据 123 条）
> 形式：本次 idea-refine 在无法与用户交互的 worker 环境中完成，关键假设已列在下方“待验证”，需人工确认。

## Problem Statement
怎样让开发者在 UserHome 里直接查到“某个任务该用哪个 Skill、它属于哪套来源、是主动调用还是按需调用”，而不必每次回到速查网页？

## Recommended Direction：静态只读目录页
- 在“工具集”分组新增侧栏入口 `SKILLHUB`，路由 `skillhub`，位于“工具集”之后、“服务”之前。
- 页面是只读目录：数据来自速查表中的 `skills` 数组，静态内嵌在代码中（`src/features/skillhub/skillCatalog.ts`），不发起网络请求，不调用任何 API。
- 三个来源（Agent Skills / Matt Pocock Skills / pstack）各带一句定位说明，和 `用途` 一起展示，便于选型。
- 只展示，不安装、不执行 Skill；速查表里的“选用清单”“星标”是浏览器本地状态，不迁移。

为什么这样：目录是信息，不是操作；静态数据让它离线可用，且没有新的后端命令或权限面。

## Key Assumptions to Validate
- [ ] “SKILLHUB”就是这个页面的菜单名。速查表里没有该词，这是本次按需求原文采用的名称。
- [ ] 速查表 v2.4 的 123 条数据就是要展示的内容，不需要和线上版本同步。
- [ ] 同名 Skill（`tdd`、`teach` 各在两个来源出现）按“来源 + 名称”区分，两条都保留。
- [ ] 只读目录已满足需求，不需要“复制安装命令”之类的动作。

## MVP Scope
- 做：侧栏入口与路由；页面标题与来源说明；搜索（名称 / 用途 / 分组）；来源筛选（全部 / 三套）；调用类型筛选（全部 / 主动 / 按需 / 原则 / 自动化 / 实验）；按分组列出条目（名称、用途、类型标签、来源标签）；中英文文案。
- 不做：见下。

## Not Doing (and Why)
- Playbook、Overlap、阶段对比、项目类型选型、Chains 流程图 — 属于速查表的“工作流 / 选型 / 回顾”章节，不是 SKILL 配置本身，范围外。
- 渠道清单（awesome 列表、skills.sh 等外部站点）— 外链与 GitHub 星数是外部数据，会过时，且与本机使用无关。
- 远程拉取最新速查表 — 引入网络依赖与缓存策略，本次不需要。
- 星标、选用清单、导出 — 速查表的个人状态；如需要，作为 v2 另立 idea。
- 修改概览、设置或其他页面 — 本次只动工具集与导航。

## 实施决定（已确认）
- 菜单名保留 `SKILLHUB`（用户指定）。它是 8 个字符，超过 `radiusAudit.test.ts` 原有的“导航标签不超过 6 个字符”规则。协调者确认采用方案 A：把该审计从字符数改为按显示宽度估算（CJK 1em，拉丁大写 0.75em，其余拉丁与数字 0.6em，空格 0.3em），上限仍为 6em，现有标签的判定结果不变。
- 审计新增断言：SKILLHUB 估算宽度（6em × 12px = 72px）小于 188px 侧栏扣除内边距与图标后的可用宽度。jsdom 无法测量真实文字，因此真机侧栏是否截断记为待人工验收。
- 目录内容（用途、分组、来源说明）是速查表的中文原文，中英文界面都显示中文；界面框架文案有英文版本。

## Open Questions
- 是否需要把“选用清单”改为本机持久化（与 UserHome 偏好存储对齐）？当前版本不做。
- SKILLHUB 是否要作为工具集里的一个 tab，而不是独立侧栏入口？当前按“菜单”理解为侧栏入口，人工确认后可改。
