# agent-incidents：错题册

本项目大部分代码由 AI agent 编写。agent 的错误里，只有越过了本该拦住它的关口的才整理成结构化记录（错题，判定见 §7），同类错题重复出现时按 §9 升级为机器可执行的规则，形成“错题 → 规则”闭环。

目录内容：

| 文件 | 作用 |
|---|---|
| `README.md` | 本文件：schema、分类、干预阶梯、规则原则 |
| `INC-NNNN.yaml` | 单条错题，一个签名一条 |
| `batch-N-proposals.md` | 第 N 批：全部 fix/revert 总表 + 规则提案 |

第一批（冷启动）见 `batch-1-proposals.md`：从主分支 100 个 `fix` 提交挖出 20 条错题和 8 条规则提案。

## 1. 错题 schema

```yaml
id: INC-0001
commit_fix: <sha>          # 修复提交
commit_origin: <sha|unknown>
related_commits: [<sha>, ...]   # 同签名的其他提交（不含 commit_fix）
area: <模块，如 services / theme / ai-config>
type: <见 §2>
symptom: <一句话>
evidence: <提交信息摘录 / diff 关键几行>
should_catch_at: <L1..L6 或 test/lint/review>
caught_at: <review|user|test|ci|unknown>
escaped_to: <none|main|user-machine|unknown>
cost: <low|mid|high>        # 影响描述；升级以 severity 为准
severity: <S1|S2|S3>        # 必填，见 §8
record_reason: [<R1..R4>, ...]  # 必填，满足的记录条件，见 §7
root_cause: <见 §3>
signature: <可用于聚类的一句话特征>
confidence: <high|low>      # 无法确定是 agent 引入时填 low
```

本批额外使用两个非必填字段：`sig_group`（对应提案文档里的签名字典编号，如 S07）和 `notes`（推断说明与验证限制）。冷启动的 INC-0001~0020 没有 `severity`、`record_reason`，允许暂时不填，复盘时补；补齐前它们的升级判断沿用 `batch-1-proposals.md`。

填写约定：

- 拿不准就写 `unknown`，不要编造；推断出来的结论在 `notes` 里写明“为推断”。
- `commit_origin` 只在追溯成本低时确认（`git log -S`、`git log -L` 或一两步 blame）。没有确认的写 `unknown` 并把 `confidence` 设为 `low`。
- `signature` 同类必须一致；同一签名只写一条 INC，其余同类提交放进 `related_commits`。
- `cost`：只描述影响面，不决定是否升级。`low` 为观感或文案；`mid` 为功能错误或用户会误判；`high` 为安全、数据丢失或越权。
- `escaped_to`：错误最远走到了哪里。没有证据就写 `unknown`，不要因为“提交在主分支上”就推断 `main`。
- 修复提交里写了“未验证/本机未运行”的，原样写进 `notes`，不得当作已验证。

## 2. 错误类型（`type`）

| 类型 | 含义 |
|---|---|
| `wrong-intent` | 理解错了需求或用户意图，做的不是被要求的事 |
| `false-done` | 声称完成但实际没完成，或验证本身有误导性（绿色但掩盖缺陷） |
| `test-cheat` | 为让检查通过而削弱、删除、绕过测试/断言/规则 |
| `scope-creep` | 超出需求范围的顺带改动，包括一个提交混入多件事 |
| `regression` | 改动破坏了此前正常的行为（典型为重构丢能力） |
| `ui-spec-drift` | 视觉/交互偏离已有规格、令牌或契约 |
| `platform-assumption` | 对操作系统、框架、外部命令的行为做了未验证的假设 |
| `missing-edge-case` | 主路径正确，边界、失败、并发、畸形输入未处理 |
| `other` | 以上都不合适；用得多说明分类要扩 |

## 3. 根因（`root_cause`）

| 根因 | 含义 |
|---|---|
| `missing-context` | agent 缺少做对所需的信息（真机样本、第三方库时序、业务约定） |
| `context-ignored` | 信息就在仓库/规格里，agent 没读或没遵守 |
| `rule-conflict` | 两条规则或两次决定互相冲突，agent 顾此失彼 |
| `vague-task` | 任务描述含糊，范围或验收标准不清 |
| `model-capability` | 信息充分、规则清晰，仍因推理/穷举能力不足而出错（**需有证据，别当默认**） |
| `env-defect` | 环境缺陷：无法在沙箱内验证、工具被拦截、缺少真机 |
| `checker-gap` | 本应有的检查（测试、lint、审计）不存在或写错，错误无人拦截 |

## 4. 七层干预阶梯（L0–L6）

从弱到强、从事后到事前。优先选能挡住该错误的**最低且足够**的一层，代价高、会越过多层才被发现的错误才往上走。选层与升级规则见 §9。

| 层 | 名称 | 手段 | 适用 |
|---|---|---|---|
| L0 | 无干预 | 靠人工审查或用户发现 | 偶发、低代价、无法形式化的错误 |
| L1 | 提示规则 | CLAUDE.md / 规则文字 | 高频、低代价、靠“记得”就能避免的约定（文案、命名） |
| L2 | 任务模板 | 派发任务的必填项与验收清单（如真机样本来源） | 错误源于任务描述缺信息 |
| L3 | 静态检查 | ESLint / stylelint / 类型 / 源码审计测试 | 能用语法或文本模式识别的契约 |
| L4 | 专项回归测试 | 针对该签名的单测、场景矩阵、样例集 | 行为类错误，需要运行才能发现 |
| L5 | 提交/CI 门禁 | hook 按 diff 特征拦截、CI 强制步骤 | 规则本身需要保护，或要求“改 A 必改 B” |
| L6 | 结构消除 | 封装、类型状态、权限收窄，使错误无法表达 | 高代价、高频、其余层反复被绕过 |

## 5. 规则必须带正反向回归用例

没有用例的规则不得进入提案的“可落地”状态：

- **正向用例（该拦的拦得住）**：取历史上真实出错的 diff 或提交（如 `<fix>^` 的文件），规则必须报错或测试必须失败；对应修复版本必须通过。
- **反向用例（不该拦的不误拦）**：规则在当前主分支全量运行结果应为零误报，或每个命中都有人工判断并记录豁免理由；另需至少一个与签名相似但合法的样例明确放行。
- 提案文档里写明构造方法：用哪个历史提交，怎么验证误报。验证不了的（如 Rust 测试在本机被拦截）要写明“未验证”及原因。
- 规则上线后，其用例与规则同等受保护，改动同样需要批准（见 §6）。

## 6. 规则变更的权限

- **worker 不得修改规则。** 规则包括：ESLint/stylelint 配置、hook、审计测试与白名单、令牌基线、既有断言的放宽或删除、本目录下已批准的提案结论。
- **规则变更须经用户批准。** 批准必须是用户明确的话，来自协调者的转述需注明出处。历史上 `f34583b`、`7842992` 等提交就因为改了审计白名单或既有断言而写明了“协调者已同意”，现在由 `scripts/check-commit-rules.mjs` 强制：改规则类文件或削弱测试的提交，必须在提交信息里带一行 `Rule-Change-Approved: <用户原话或批准出处>`，协调者合并前与 CI 都会检查；协调者需核对出处属实。
- worker 发现规则本身有问题时，把问题写进汇报或新增 INC，不要自己改规则让检查变绿。
- 新增 INC、追加 `related_commits`、补充 `notes` 属于普通文档维护，不算规则变更。

## 7. 什么时候记录

### 先分清“迭代”和“错题”

- **迭代**：worker 在交付（`worker_done`）之前自己发现并改正的错误，例如测试红了再修绿、lint 报错后修好。这是正常工作过程，不记录。
- **错题**：错误越过了本该拦住它的那道关口。

### 记录条件（满足任意一条才记）

| 编号 | 条件 |
|---|---|
| R1 逃逸 | worker 交付之后才被发现，发现者是协调者复核、独立审查、CI、合并后检查或用户 |
| R2 人工代价 | 需要用户纠正、返工，或让用户做了本可避免的决定 |
| R3 实际损失 | 回滚、revert、改写历史；写入了真实 `~` 或用户数据；泄漏了凭据或敏感信息；返工超过一次额外派发 |
| R4 高危近失 | 属于不可逆操作类别（push/force、改写历史、删除、写真实 `~`、凭据或脱敏），过程违规，**并且当时没有可恢复手段**（没有备份、reflog 覆盖不到、发生在 worktree 之外）。结果正确也要记 |

### 不记录

| 编号 | 情形 |
|---|---|
| N1 | 交付前已经自行纠正（属于迭代） |
| N2 | 结果正确、没有代价、并且可以恢复的过程偏差，只在 worker 汇报里写明 |
| N3 | 首次出现的环境偶发问题（网络、flaky）；同一现象第二次出现时才记，`root_cause: env-defect` |
| N4 | 需求变化，用户改主意不算错误 |
| N5 | 检查器按设计拦下了问题（L4/L5 正常生效）；只给该规则的命中次数加一，不记错题 |

规则命中次数由协调者汇总在对应的 `batch-N-proposals.md`，供 §9 的退役判断使用。

### 谁来记、什么时候记

- 由**协调者**在验收时判断，worker 不记录。
- 每次拒收或纠正，协调者都要在汇报里写明“记 / 不记”，以及依据哪一条（R1–R4 或 N1–N5）。

## 8. 严重度

| 级别 | 含义 |
|---|---|
| S1 高 | 漏到用户真机或用户数据、安全或脱敏泄漏、不可逆的损失（包括所有 R4） |
| S2 中 | 已进入 main、需要回滚或改写历史、用户返工 |
| S3 低 | 交付后被协调者复核或审查拦下，没有进入 main |

## 9. 升级、退役与选层

升级按 `signature` 聚类，次数按 INC 本身加 `related_commits` 条目计：

| 严重度 | 升级条件 |
|---|---|
| S1 | 出现 1 次就升级，直接上机器层（L4–L6）；规则生效之前暂停分发同类任务 |
| S2 | 同一签名出现第 2 次时升级。第 1 次只记录，可以顺手补一条 L1（任务卡或上下文），不算升级 |
| S3 | 同一签名在最近 50 个任务内累计出现 3 次时升级 |

- 规则生效后同一签名又出现：说明规则无效，修这条规则或把它上调一层，不要再加一条平行的规则。
- 根因是 `model-capability`：升级方式是调整路由（这类任务换模型，见 AGENTS.md §10），不加规则。
- **选层**：能机械判定的放 L4/L5；不能机械判定的放 L2/L3；能从结构上消除的放 L6。在满足 §4“最低且足够”的前提下选择。
- **退役**：规则在最近 100 个任务内 0 命中，且错误已被 L6 从结构上消除，就退役。文字规则被机器规则覆盖后，删掉文字规则。
- 升级和退役都以提案批次交给用户批准（见 §6）。

## 10. 维护流程

1. 验收时按 §7 判断；该记的按 §1 写一条 INC，同签名已有 INC 的只追加 `related_commits`。
2. 按 §9 判断是否进入提案候选。
3. 提案按 §9 选层，按 §5 写正反向用例，交用户批准后才实现。
4. 实现规则后，回写对应 INC 的 `should_catch_at`，并观察同类提交是否减少。
5. `batch-N` 用新的 `git log` 区间增量生成，不要重写旧批次。
